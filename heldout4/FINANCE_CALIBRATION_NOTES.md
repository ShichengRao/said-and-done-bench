**Procurement version 3 revision record — durable execution workflow**

After all version-2 model runs completed, the parent authorized a substantive workflow change. Version 3 supplies the independently validated exact planner as protected support and requests the missing procurement execution feature: a durable SQLite reservation service shared by multiple buyers. Correct draft optimization alone does not prevent two buyers from promising the same physical lot or a retried checkout from consuming stock twice. The requested service must integrate persisted availability with the planner, hold multi-pool allocations atomically, commit or release them, expire holds using logical timestamps, check optimistic versions, persist operation identities and their original replies across restarts, and serialize competing callers. This is a separate business-state engineering problem; no further static optimization constraints were added to exploit a prior answer.

The contract explicitly states replay-before-time/expiry, equality by JSON data including meaningful list order, rollback of tentative expiry on rejected operations, accepted/replayable unavailable responses, permanent reservation IDs, and versioned terminal states.
