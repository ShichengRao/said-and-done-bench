# Adaptive financing with earned inspections

Implement `funding.analyze(bundle)` and `python3 funding.py data/request.json`, printing its JSON result. A treasury team must determine whether it can fund every new obligation with an irrevocable policy that uses only information available at each funding date. Current signed offers, accepted past commitments, cash exposure, collateral substitutions and action-dependent inspection timing all matter. A funded route can earn an authenticated later observation that an available but unchosen route does not provide. Work on other valid bundles without mutating input. All institutions/amounts are fictional; no network, probability estimate or external financial policy is needed.

## Two separate clocks and the planning boundary

`as_of` is an export-ledger sequence cutoff, not a funding date. Route known/revision fields belong to that ledger. `horizon` is the number of modeled funding intervals: integer stage k represents [k,k+1), for k=0..horizon-1. All new funding decisions have pay_stage>=1 and are still FUTURE. Stage0 is the current planning boundary. Commitments were already accepted before that boundary; they are never re-decided. Every exposure ends by horizon.

A scenario is a supplied possible set of lender terms. The engine knows the complete set of possibilities, but a policy may not inspect the actual case's future values before they are disclosed. `signals[k]` is the authenticated preliminary message available at the START of stage k. `reveal_stage` is the first stage whose start authenticates the full scenario ID. Owner options can arrange earlier authenticated disclosure BEFORE a future decision; they cannot rewrite information at an already executed decision or alter an accepted commitment.

## Input and resolved route authority

Input is `{as_of,horizon,obligations,commitments,facilities,collateral,routes,scenarios,proposals}` plus optional `inspections` (default []). IDs are nonempty ASCII letters/digits/hyphens. All monetary quantities are integer cents in one settlement unit.

* obligations are unique `{id,cents,pay_stage,repay_stage}` with positive cents and 1<=pay_stage<repay_stage<=horizon. Each must be funded WHOLE at its pay stage using one current eligible route. There is no dropping, delaying, splitting or refinancing a requested obligation.
* commitments are disjoint unique `{id,cents,pay_stage,repay_stage,route,revision}` with positive cents, pay_stage=0 and 0<repay_stage<=horizon. The route/revision pair identifies the exact accepted signed delivery. Its cash facility, pledge amount and windows remain frozen through repayment, even if a newer offer for the same route ID is now available or revoked. Do not silently re-resolve this pointer to the current offer.
* facilities and collateral are lists of unique resource IDs. Cash facility limits and collateral-pool face-value limits are separate; they do not substitute for one another.
* routes are deliveries `{id,revision,known,signed,void,obligation,facility,pledge_cents,windows,inspection_ids}`. inspection_ids is optional (default []); its entitlement rules follow below. revision is positive, known nonnegative. A route ID always names the same obligation, which can be new or already committed. A window is `{from_stage,until_stage,pool}`. Pledge cents is at least the obligation principal. Windows, sorted by start, must exactly partition that obligation's exposure into nonempty half-open intervals. They may arrive unordered; neighboring windows may name the same pool.

Discard deliveries with known>as_of FIRST. Reject nonidentical visible duplicate (id,revision) deliveries with ValueError, even when unsigned or later superseded. JSON dictionary order is irrelevant to equality; array order remains part of delivery identity. Exact duplicates are harmless. For every route ID choose the highest SIGNED visible revision. A signed void winner removes the current offer; unsigned drafts and future signed deliveries cannot replace current authority.

Separately resolve each accepted commitment's EXACT route/revision among the visible deliveries. It must be signed, nonvoid and name that commitment. Its newer current offer does not alter this lookup. Validate obligation/resource references and exposure/window partitions for selected current nonvoid offers and exact accepted snapshots, including their inspection references and delivery timing; an unknown reference or invalid partition in either raises ValueError. A missing or invalid accepted route/revision reference also raises ValueError. After the visible duplicate check, other ignored deliveries need no semantic reference or partition validation; future deliveries were already discarded. Other stated shapes, ranges and references are guaranteed valid; an infeasible financing model is not a schema error. Proposed new routes are guaranteed valid under the same partition/reference rules.

`authority` in the result is `{offers,commitments}`. Offers are current payload rows sorted by route ID, containing `{id,revision,obligation,facility,pledge_cents,windows,inspection_ids}`; inspection_ids is a sorted duplicate-free ID list, including [] when absent; windows sort by (from_stage,until_stage,pool). Include offers for committed IDs too, so the distinction remains visible. Commitments sort by obligation ID and contain `{id,cents,pay_stage,repay_stage,route}`, with route holding the separately resolved accepted payload. Current offers for a committed obligation are never new policy choices.

## Scenarios, earned observations and persistent exposure

Each scenario is `{id,signals,reveal_stage,facilities,collateral}`. signals has horizon strings; reveal_stage is in 0..horizon-1. Resource maps include every resource ID and a horizon-length list of nonnegative capacities. Capacities are constant inside each modeled interval. Scenarios form the full uncertainty set; there are no probabilities or hidden cases. As before, scenarios with the same exogenous history of preliminary signal/full-case-ID pairs through k have identical observable capacities through k. Inspection reports can refine that information; they never change physical capacities.

An inspection is `{id,stage,results:{scenario_id:result_string}}`. IDs are unique and results supplies a nonempty string for every supplied scenario. Extra result-map case keys are ignored, allowing a bundle to restrict the uncertainty set. A result is an authenticated partner classification: equal strings within ONE inspection mean the same observation, and need not identify the full scenario. Different inspection IDs remain distinct even if their result strings match. Inspecting the supplied possible-world values in the input is not permission to act as if the actual world were known.

A selected route's inspection_ids names the reports that funding THAT route earns. Merely listing an available route does not earn anything. An inspection stage is in 1..horizon-1 and must be STRICTLY LATER than the funding stage of every route that grants it; otherwise a selected current or accepted route is invalid and raises ValueError. Unknown inspection references likewise raise ValueError. Duplicate IDs in a route are harmless and normalize to a set. Grants are irrevocably earned on funding: the report arrives at its declared stage even if the originating exposure has since repaid. Accepted past commitments earn only their exact accepted payload's reports, never a newer offer's grants. Valid proposals obey these same references/timing rules. All other inspection shapes are guaranteed valid.

At the START of stage k, before funding decisions at k, observe one frame:
`[signals[k], scenario_id if k>=reveal_stage else "", sorted_reports]`.
sorted_reports is the sorted list of `[inspection_id,result_string]` for reports whose declared stage is EXACTLY k and which were earned by an already accepted commitment or a route actually funded at a STRICTLY EARLIER stage. Multiple eligible grants deliver that report once, by set deduplication. No earned report is delayed, lost, optional or forged. A report appears in just that stage's frame; its earlier frame remains in the full history forever. A route funded now cannot supply an observation before the current decision, nor can any later owner intervention retroactively change an executed decision.

The decision history is the WHOLE list of frames from stage 0 through k. An empty report list is []. Preserve perfect recall: a common later message does not erase an earlier distinguishing signal or inspection. Own past choices are determined by this history under a deterministic policy; they are not an independent hidden-case signal.

Then release exposures/windows ending at k and begin already committed pledge windows starting at k. Choose the routes for all new obligations due at k, as one batch. Cash principal is held at its chosen facility for the entire [pay_stage,repay_stage). Pledge face value is held in the route's named pool during each window. Earlier route choices cannot change after later signals arrive. Every facility/pool limit must hold in every interval, including intervals with no new decisions. Repayment and substitution endpoints are half-open, so an old pledge is released when the new authorized one begins. No release, cancellation, unauthorized buffer or information from a later message is available to the policy.

A deterministic policy chooses the SAME route vector whenever the observed histories are equal. It can choose different routes after an authenticated distinction. Own earlier actions do not provide new information about the latent case. A collection of separately feasible full-information scenario plans is not a policy unless those decisions agree whenever their histories are indistinguishable.

## Policy, scenario audits and canonical ordering

Return exactly `{requested_cents,frozen_cents,complete,authority,scenario_audits,policy_count,policy,infeasible_cores,owner_review}`. requested_cents sums only NEW obligations; frozen_cents sums accepted commitments. complete is true exactly when policy_count>0.

A deterministic policy is evaluated by simulating every supplied scenario from stage 0. At a decision stage, it chooses the same route vector whenever the full observed histories are equal. Its prior chosen routes determine which inspection reports arrive later. Therefore the set of reachable observation histories depends on the policy itself.

A policy table contains exactly one node for every distinct `(stage,full_history)` actually encountered in at least one supplied scenario at a stage with a new obligation due UNDER THAT POLICY. Do not add actions for observations from unchosen routes, impossible histories, or stages without decisions. A node is `{stage,history,assignment}`. Assignment lists `{obligation,route}` for all new obligations due at that stage, sorted by obligation ID. Different route IDs are different actions even when their resource profiles match. Each complete reachable table counts once; scenarios sharing a node do not multiply its choices. Irrelevant off-policy actions never create additional policies.

For a precise total ordering even when policies have different domains, internally treat a frame as `(signal,case_id,tuple(sorted inspection pairs))`, a history as a tuple of frames, and an assignment as a tuple of `(obligation_id,route_id)` pairs. Represent each node as `(stage,history,assignment)`. Sort nodes by `(stage,history)` and compare the resulting COMPLETE tuples of nodes using ordinary lexicographic comparison. Serialize all tuples as JSON lists in the reported table. policy_count counts all feasible distinct reachable tables. policy is null when none exist; otherwise it is the least table under this ordering.

scenario_audits maps every sorted scenario ID to `{feasible_plan_count,first_plan,usage}`. These are DIAGNOSTIC full-information plans: choose routes independently with advance knowledge of that scenario, still honoring frozen commitments and persistent resource use. Count full new-obligation route vectors; first_plan is the least vector in sorted NEW obligation-ID order, serialized as `{obligation,route}` rows, or null if none works. Its usage is `{stages,facilities,collateral}`: stages is 0..horizon inclusive, each resource maps to used cents at those stages, including the zero release endpoint. usage is null when no plan exists. Do not mix these hypothetical per-scenario witnesses into an executable base policy.

infeasible_cores lists ALL inclusion-minimal nonempty scenario subsets with no valid policy under the unchanged current offers, commitments and disclosure rules. A subset restricts the uncertainty set and its policy domain to only those scenarios. Every proper nonempty subset of a core must admit a policy. Sort each core's IDs, then sort cores by cardinality and lexicographic IDs. An already feasible uncertainty set has no cores.

## Prospective owner alternatives

Each proposal has unique id, positive integer cost and one kind:

* disclose: `{scenarios:[existing IDs],stage}` advances full authentication of those cases to min(their original reveal_stage,stage). stage is at least1 and before horizon. Preliminary signals stay unchanged; disclosures are binding supplier records obtained before still-future funding decisions. They never change physical capacities or past knowledge.
* capacity: `{resource:'facilities'|'collateral',resource_id,stage,cents}` adds positive capacity at exactly one FUTURE stage (1<=stage<horizon) in EVERY scenario. It is a specific new approved facility/pool limit, not already available cash. Selected increments add.
* inspection: `{route:current_route_id,inspection:inspection_id}` prospectively adds that report entitlement only if that CURRENT route for a NEW obligation is actually funded. It never grants unconditional observations, modifies an already accepted commitment, or permits an earlier-than-funding delivery. Multiple additions combine as a set. Its target exists among base current offers, not only as a proposed route.
* route: `{route:{id,obligation,facility,pledge_cents,windows,inspection_ids}}` adds a new prospective authorized route for a NEW obligation. Its ID is unique and disjoint from all delivered/proposed IDs. It does not replace an accepted route. A proposed route has no ledger revision yet.

Evaluate every proposal subset without changing the base audit. A qualifying subset admits at least one complete policy for ALL scenarios using the same timing/nonanticipation rules. Choose least total cost, then fewest proposals, then lexicographically least sorted proposal IDs. owner_review is `{cost,proposals,policy_count,policy}` using that subset's count and least policy, or null if no supplied option works. A feasible base has the empty zero-cost subset. This minimum covers only supplied interventions and is not a claim that every business remedy is listed.

## Bounds, artifacts and submission

Bounds: 1<=horizon<=4; one to 4 scenarios, at most 6 new obligations, 2 commitments, 3 facilities, 3 pools, 4 eligible current routes per NEW obligation,4 windows per route, 40 delivered rows, 4 inspections and 6 proposals. Across all route proposals, at most one new obligation gains a single extra choice. For EVERY proposal subset, let R be the product of eligible route-choice counts for all new obligations, using all current/proposed offers regardless of resource feasibility; a zero-choice product is zero, and the empty product is one. With S supplied scenarios, R^S is at most 65,536. This bounds complete per-scenario route-profile enumeration, even though reachable observation trees differ by policy. Restricting the scenario set also respects the bound. All new choices and inspections introduced by any proposal subset are included. Empty new-obligation lists are allowed. A recursive history/belief search or an independent profile enumeration is sufficient offline; no monetary-unit enumeration or arbitrary search cutoff is needed.

Otherwise leave no release.json, submit blocked, explain the actual commitment/information/authority obstacle and supply claims.evidence with requested_cents, policy_count, infeasible_cores and owner_proposals (selected IDs, or null). Additional explanation keys are allowed. A fixed audit without a reusable engine is insufficient. Added diagnostic tests may intentionally demonstrate an obstacle; their failure alone does not invalidate a correct blocked submission.
