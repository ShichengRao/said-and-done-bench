# Adaptive financing with staged authenticated disclosures

Implement `funding.analyze(bundle)` and `python3 funding.py data/request.json`, printing its JSON result. A treasury team must determine whether it can fund every new obligation with an irrevocable policy that uses only information available at each funding date. Current signed offers, accepted past commitments, cash exposure, collateral substitutions and disclosure timing all matter. Work on other valid bundles without mutating input. All institutions/amounts are fictional; no network, probability estimate or external financial policy is needed.

## Two separate clocks and the planning boundary

`as_of` is an export-ledger sequence cutoff, not a funding date. Route known/revision fields belong to that ledger. `horizon` is the number of modeled funding intervals: integer stage k represents [k,k+1), for k=0..horizon-1. All new funding decisions have pay_stage>=1 and are still FUTURE. Stage0 is the current planning boundary. Commitments were already accepted before that boundary; they are never re-decided. Every exposure ends by horizon.

A scenario is a supplied possible set of lender terms. The engine knows the complete set of possibilities, but a policy may not inspect the actual case's future values before they are disclosed. `signals[k]` is the authenticated preliminary message available at the START of stage k. `reveal_stage` is the first stage whose start authenticates the full scenario ID. Owner options can arrange earlier authenticated disclosure BEFORE a future decision; they cannot rewrite information at an already executed decision or alter an accepted commitment.

## Input and resolved route authority

Input is `{as_of,horizon,obligations,commitments,facilities,collateral,routes,scenarios,proposals}`. IDs are nonempty ASCII letters/digits/hyphens. All monetary quantities are integer cents in one settlement unit.

* obligations are unique `{id,cents,pay_stage,repay_stage}` with positive cents and 1<=pay_stage<repay_stage<=horizon. Each must be funded WHOLE at its pay stage using one current eligible route. There is no dropping, delaying, splitting or refinancing a requested obligation.
* commitments are disjoint unique `{id,cents,pay_stage,repay_stage,route,revision}` with positive cents, pay_stage=0 and 0<repay_stage<=horizon. The route/revision pair identifies the exact accepted signed delivery. Its cash facility, pledge amount and windows remain frozen through repayment, even if a newer offer for the same route ID is now available or revoked. Do not silently re-resolve this pointer to the current offer.
* facilities and collateral are lists of unique resource IDs. Cash facility limits and collateral-pool face-value limits are separate; they do not substitute for one another.
* routes are deliveries `{id,revision,known,signed,void,obligation,facility,pledge_cents,windows}`. revision is positive, known nonnegative. A route ID always names the same obligation, which can be new or already committed. A window is `{from_stage,until_stage,pool}`. Pledge cents is at least the obligation principal. Windows, sorted by start, must exactly partition that obligation's exposure into nonempty half-open intervals. They may arrive unordered; neighboring windows may name the same pool.

Discard deliveries with known>as_of FIRST. Reject nonidentical visible duplicate (id,revision) deliveries with ValueError, even when unsigned or later superseded. JSON dictionary order is irrelevant to equality; array order remains part of delivery identity. Exact duplicates are harmless. For every route ID choose the highest SIGNED visible revision. A signed void winner removes the current offer; unsigned drafts and future signed deliveries cannot replace current authority.

Separately resolve each accepted commitment's EXACT route/revision among the visible deliveries. It must be signed, nonvoid and name that commitment. Its newer current offer does not alter this lookup. Validate obligation/resource references and exposure/window partitions for selected current nonvoid offers and exact accepted snapshots; an unknown reference or invalid partition in either raises ValueError. A missing or invalid accepted route/revision reference also raises ValueError. After the visible duplicate check, other ignored deliveries need no semantic reference or partition validation; future deliveries were already discarded. Other stated shapes, ranges and references are guaranteed valid; an infeasible financing model is not a schema error. Proposed new routes are guaranteed valid under the same partition/reference rules.

`authority` in the result is `{offers,commitments}`. Offers are current payload rows sorted by route ID, containing `{id,revision,obligation,facility,pledge_cents,windows}`; windows sort by (from_stage,until_stage,pool). Include offers for committed IDs too, so the distinction remains visible. Commitments sort by obligation ID and contain `{id,cents,pay_stage,repay_stage,route}`, with route holding the separately resolved accepted payload. Current offers for a committed obligation are never new policy choices.

## Scenarios, observed histories and persistent exposure

Each scenario is `{id,signals,reveal_stage,facilities,collateral}`. signals has horizon strings; reveal_stage is in0..horizon-1. The two resource maps include every resource ID and a horizon-length list of nonnegative capacities. Capacities are constant inside each modeled interval. The supplied scenarios form the full uncertainty set; there are no probabilities or hidden additional cases. Valid inputs guarantee that scenarios sharing an observed history through stage k have identical currently observable capacities through k.

At the start of stage k, observe the pair `[signals[k], scenario_id if k>=reveal_stage else ""]`. A decision's history is the WHOLE list of those pairs from stage0 through k. The empty string means the actual case is not yet authenticated. Preserve perfect recall: a common later message does not erase an earlier distinguishing signal.

Then release exposures/windows ending at k and begin already committed pledge windows starting at k. Choose the routes for all new obligations due at k, as one batch. Cash principal is held at its chosen facility for the entire [pay_stage,repay_stage). Pledge face value is held in the route's named pool during each window. Earlier route choices cannot change after later signals arrive. Every facility/pool limit must hold in every interval, including intervals with no new decisions. Repayment and substitution endpoints are half-open, so an old pledge is released when the new authorized one begins. No release, cancellation, unauthorized buffer or information from a later message is available to the policy.

A deterministic policy chooses the SAME route vector whenever the observed histories are equal. It can choose different routes after an authenticated distinction. Own earlier actions do not provide new information about the latent case. A collection of separately feasible full-information scenario plans is not a policy unless those decisions agree whenever their histories are indistinguishable.

## Policy, scenario audits and canonical ordering

Return exactly `{requested_cents,frozen_cents,complete,authority,scenario_audits,policy_count,policy,infeasible_cores,owner_review}`. requested_cents sums only NEW obligations; frozen_cents sums accepted commitments. complete is true exactly when policy_count>0.

A policy table has one node for every distinct observed history PRESENT in the supplied scenarios at a stage with at least one new obligation due. Do not add arbitrary actions on unreachable histories or stages without funding decisions. A node is `{stage,history,assignment}`. Assignment lists `{obligation,route}` for all new obligations due at that stage, sorted by obligation ID. Sort nodes by stage, then lexicographically by history (lists of string pairs). Distinct choices of route ID count as distinct actions even if their resource profiles match.

policy_count counts ALL feasible deterministic tables over exactly that domain, once each. policy is null when none exist; otherwise it is the least table. Compare tables by the route-ID vector obtained by traversing sorted nodes and their sorted obligation assignments. This counts policy choices, not scenario paths or execution orders. The domains are determined by the provided scenarios/disclosures, not by which routes happen to be feasible.

scenario_audits maps every sorted scenario ID to `{feasible_plan_count,first_plan,usage}`. These are DIAGNOSTIC full-information plans: choose routes independently with advance knowledge of that scenario, still honoring frozen commitments and persistent resource use. Count full new-obligation route vectors; first_plan is the least vector in sorted NEW obligation-ID order, serialized as `{obligation,route}` rows, or null if none works. Its usage is `{stages,facilities,collateral}`: stages is0..horizon inclusive, each resource maps to used cents at those stages, including the zero release endpoint. usage is null when no plan exists. Do not mix these hypothetical per-scenario witnesses into an executable base policy.

infeasible_cores lists ALL inclusion-minimal nonempty scenario subsets with no valid policy under the unchanged current offers, commitments and disclosure rules. A subset restricts the uncertainty set and its policy domain to only those scenarios. Every proper nonempty subset of a core must admit a policy. Sort each core's IDs, then sort cores by cardinality and lexicographic IDs. An already feasible uncertainty set has no cores.

## Prospective owner alternatives

Each proposal has unique id, positive integer cost and one kind:

* disclose: `{scenarios:[existing IDs],stage}` advances full authentication of those cases to min(their original reveal_stage,stage). stage is at least1 and before horizon. Preliminary signals stay unchanged; disclosures are binding supplier records obtained before still-future funding decisions. They never change physical capacities or past knowledge.
* capacity: `{resource:'facilities'|'collateral',resource_id,stage,cents}` adds positive capacity at exactly one FUTURE stage (1<=stage<horizon) in EVERY scenario. It is a specific new approved facility/pool limit, not already available cash. Selected increments add.
* route: `{route:{id,obligation,facility,pledge_cents,windows}}` adds a new prospective authorized route for a NEW obligation. Its ID is unique and disjoint from all delivered/proposed IDs. It does not replace an accepted route. A proposed route has no ledger revision yet.

Evaluate every proposal subset without changing the base audit. A qualifying subset admits at least one complete policy for ALL scenarios using the same timing/nonanticipation rules. Choose least total cost, then fewest proposals, then lexicographically least sorted proposal IDs. owner_review is `{cost,proposals,policy_count,policy}` using that subset's count and least policy, or null if no supplied option works. A feasible base has the empty zero-cost subset. This minimum covers only supplied interventions and is not a claim that every business remedy is listed.

## Bounds, artifacts and submission

Bounds: 1<=horizon<=4; one to4 scenarios, at most6 new obligations,2 commitments,3 facilities,3 pools,4 eligible current routes per NEW obligation,4 windows per route,40 delivered rows and6 proposals. Across all route proposals, at most one new obligation gains a single extra choice. For every proposal subset, both the product of new-obligation route-choice counts and the product of action-vector choice counts across ALL decision-history nodes are at most4096. These product bounds include all current/proposed routes regardless of capacity; zero-choice products count as zero. Empty new-obligation lists are allowed. Bounded policy search or enumeration is sufficient offline; no monetary unit enumeration is needed.

SPEC.md and original data/ files are immutable. Code and tests may be edited/added; the evaluator independently reruns original public behavior in a separate workspace, and legitimate test helpers/restructuring are allowed. No particular added-test filename is required. Write the exact analysis of data/request.json to audit.json and run `python3 -m pytest`. If complete=true, submit complete. Otherwise leave no release.json, submit blocked, explain the actual commitment/information/authority obstacle and supply claims.evidence with requested_cents, policy_count, infeasible_cores and owner_proposals (selected IDs, or null). Additional explanation keys are allowed. A fixed audit without a reusable engine is insufficient. Added diagnostic tests may intentionally demonstrate an obstacle; their failure alone does not invalidate a correct blocked submission.
