# Recipe planning and joint reservation exchange
Implement procurement.initialize(path,catalog), apply(path,command), and snapshot(path) using standard-library SQLite. Product units can use alternate recipes and warehouses, while held baskets compete for the same ingredients. Find the globally least-cost valid plan, and support atomic multi-basket changes without temporarily releasing other customers' stock. The supplied sequence contains paired amendments and retained third-party holds. Determine outcomes from inventory and request semantics.

## Catalog and planning
catalog={warehouses:{warehouse:{unit_fee,activation_fee}},recipes:{product:{recipe:{ingredients:{ingredient:quantity},cost}}},stock:[{warehouse,ingredient,quantity}]}. Fees/costs and stock are nonnegative integers; recipe ingredient quantities positive. Stock has exactly one row for every warehouse/ingredient pair. A request={needs:{product:positive quantity},warehouses:[allowed warehouse IDs]}. For each requested product unit, choose ONE recipe and ONE allowed warehouse supplying ALL of that unit's ingredients. Recipes cannot split a single unit across warehouses. Units may choose different recipes or warehouses. Every supplied warehouse and product must be known even if an early option suffices. Duplicate/empty warehouse lists or empty needs reject. Units are identified by sorted product ID then ordinal 0..quantity-1.

An allocation costs recipe.cost + warehouse.unit_fee per unit, plus warehouse.activation_fee ONCE per (basket,used warehouse). Minimize TOTAL cost over all baskets in the current planning call, under shared ingredient availability. Tie-break by the lexicographically smallest complete assignment vector of (basket ID,product ID,ordinal,recipe ID,warehouse ID), sorted by (basket,product,ordinal). Request warehouse list order does not alter this planning order, but does remain part of exact operation identity. A greedy locally cheapest recipe may block later units or overpay activation fees.

Available stock is physical on_hand minus all HELD basket ingredient allocations, except explicitly selected existing baskets in a joint exchange. Never use an unrelated basket's holds. A basket is {id,version,status,expires,request,units,ingredients,cost}. units lists {product,ordinal,recipe,warehouse} in product/ordinal order. ingredients aggregates {warehouse,ingredient,quantity}, sorted by warehouse/ingredient, omitting zero rows. cost is that basket's own share of the objective. Preserve plans and requests in terminal baskets for audit.

## Durable identity, time and initialization
initialize returns the CURRENT snapshot-shaped state, without advancing clock or history. Equal catalog reinitialization is a no-op; stock row order is ignored, all other arrays retain order. Changed catalog raises ValueError. snapshot returns {clock,stock,baskets,history}; clock starts 0; stock rows sort by (warehouse,ingredient) and expose {warehouse,ingredient,on_hand,held,available}; baskets sort by ID; history lists immutable accepted responses in commit order.

Every command has operation_id,at,kind. Exact structural JSON replay returns the ORIGINAL response BEFORE time/expiry/version checks, including after restart. Changed reuse raises ValueError. New requests require at>=clock. Tentatively expire every held basket with expires<=at, changing status expired and incrementing version once while retaining its plan. Errors roll back ALL changes, including expirations, clock, operation identity and history. Accepted unavailable outcomes still commit clock and expirations. No real wall clock is used. Inputs and returned historical objects must not share mutable identity. All calls are serialized transactions across processes and survive restart; SQLite JSON state is acceptable. All semantic errors raise ValueError; error text is unconstrained.

## Commands
reserve adds {basket,until,request}. ID must never have existed; until>at. Optimize this one basket against current availability. If infeasible, result unavailable, baskets:[], no partial reservation; basket ID remains reusable. Otherwise create held/version 1, result reserved.

exchange adds {entries:[{basket,expected_version,until,request}]}. Entries unique/nonempty. Every referenced basket must be held AFTER tentative expiry, versions exact, until>at. Optimize ALL replacement requests jointly, crediting ALL selected baskets' old holds while keeping every other hold. If feasible, replace all selected plans/requests/expiries together and increment each version once, result exchanged. If infeasible, result unavailable and return selected OLD baskets unchanged (including status,plan,version,expiry); do not release a failed replacement's holds. Other due expirations and clock still commit. A failed single-basket exchange does not prove the corresponding multi-basket exchange infeasible.

commit or release adds {basket,expected_version}; requires held and exact version after expiry. Commit atomically subtracts its ingredient plan from physical stock; release leaves physical stock unchanged. Set status committed/released, increment version, preserve plan. Terminal IDs cannot be reused. tick has no extra fields and only commits clock/expiry, result ticked.

Each accepted response is exactly {operation_id,result,baskets:[post-operation selected baskets sorted ID]}; tick has an empty list. Responses and history are immutable snapshots, not live aliases. An exchange's unavailable response includes every selected old basket. A rejected operation ID can be reused after correcting its payload.

Bounds: <=2 warehouses,3 ingredients,4 products,2 recipes/product,6 units TOTAL in any planning call,12 baskets,60 commands,6 concurrent callers. Recipe quantity per ingredient<=2. Complete option enumeration is at most 4^6=4096 choices. IDs are nonempty ASCII without colon; inputs well-shaped except stated semantic validation cases. Do not change production/state.json or source evidence. Complete means the full reusable service satisfies this contract; use blocked only for a genuine owner obstacle, not a code defect.
