# Atomic approval-history reconciliation
Repair release_audit.audit(data) and its CLI `python release_audit.py data/input.json`. Bracken Sound requests a compliance attestation for the exact supplied receipt scope. These are observations of a multi-service authorization coordinator, not future deployment permissions. Reconcile authenticated revision histories, then determine whether any legal atomic execution explains ALL observed outcomes and timing. Produce bounded evidence, local resource projections, a smallest inconsistent scope if any, and cheapest owner-approved scope-correction proposal. Never change historical outcomes or retroactively create approvals.

## Reconstruction
initial maps resource to integer fence value. scope lists unique operation IDs. keys is the trusted RSA public-key registry consumed by supplied crypto.py. grants has {id,revision,principal,keyid,resources,valid_from,valid_to,revoked}; operations contains signed envelopes {signed:operation,signatures:[{keyid,sig}]}. Use greatest integer revision for each grant ID and each signed operation ID, independent of arrival. Identical duplicates allowed; unequal same-ID/same-revision records raise ValueError even when superseded. Signature verification covers the whole selected operation body using supplied crypto.verify_signature; implementing crypto is not requested.

operation={id,revision,principal,invoke,respond,expected:{resource:value},writes:{resource:value},success:boolean}. invoke<respond; every resource exists in initial. A selected operation is authenticated iff a latest grant for its principal is unrevoked, covers ALL read/write resources, is valid for the entire closed invoke..respond interval, and its keyid has a valid operation signature. One qualifying grant must cover the complete operation; do not combine partial grants. Missing scoped operation reason missing; no eligible grant reason grant; eligible grant but no valid signature reason signature (priority order). Ignore unscoped operation records after revision conflict checking. No input mutation.

## Exact atomic semantics
At a single linearization point within its window, an operation compares ALL expected fences with current state. If all equal, result MUST be success=true and its writes happen atomically (an empty write map is a successful read-only operation). Otherwise result MUST be false and no write happens. Failed operations are real observed outcomes, not receipts that can simply be omitted. Successful writes may replace with any nonnegative value; this format is not a per-resource increment counter.

Any A.respond<=B.invoke requires A before B. Overlapping operations may occur in either order. A legal history is a permutation of the scoped authenticated operations satisfying these real-time constraints and all observed results. When analyzing a subset for a correction/core, omitted operations do not execute; initial is unchanged and real-time constraints are restricted to remaining operations. If authentication fails, that scope has no legal attestation. Future authority cannot fix its historical observations.

Explore prefix states (done-set,current resource values), merging equal states. Include initial. State encoding is canonical JSON string [sorted done IDs,{resource:value}], sort_keys=True,separators=(',',':'),ensure_ascii=True. Sort these strings, canonical-encode the list, SHA256 it. History result fields: legal:boolean, history:lexicographically smallest full legal permutation or null, max_prefix:lexicographically smallest maximum-length legal prefix, reachable_count and reachable_sha256. If scoped authentication fails, full history field is null. Bounds <=10 operations,<=6 resources,<=8 owner proposals; all state enumeration is finite. Hash describes ALL reachable prefix states, not just a chosen path.

For each resource, separately project each authenticated touching operation's expected/writes to that resource and apply the SAME observed result and timing rules. projections maps resource to whether that projected history is legal. This is diagnostic only: separate legal histories need not compose. minimal_core is empty if certifiable, otherwise the inconsistent scope minimizing (cardinality,sorted ID list). Invalid authentication counts as inconsistent.

owner_requests are {id,withdraw:[scoped IDs],cost:positive integer}. A hypothetical selected subset withdraws the union from attestation scope, without altering evidence. Pick a sufficient subset minimizing (cost,sorted proposal IDs) whose remaining scope has a legal history; report {cost,requests,remaining_scope,history}. No sufficient proposal gives null. The empty request set is eligible. Empty scope has the empty legal history. The owner must actually approve the corrected scope; proposals are not applied to the original certification request.
