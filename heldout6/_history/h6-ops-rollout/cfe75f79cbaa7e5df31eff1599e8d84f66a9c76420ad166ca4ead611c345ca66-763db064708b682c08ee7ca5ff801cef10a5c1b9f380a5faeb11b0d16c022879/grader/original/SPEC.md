# Concurrent rollout outbox
Repair controller.py for an offline, durable deployment controller with dependency-DAG plans and a three-command window. Dispatch reserves resources but is not observed success. Receipts can arrive in any order, fail independently, be duplicated, or arrive after a newer epoch. The supplied production plan requires parallel compatible copies followed by safe retirement, across two zones.

## Persistent API
initialize(path,configuration), inspect(path), apply(path,request), with SQLite path. configuration={nodes:{node:{rack,zone,capacity}},rack_capacity:{rack:integer},services:{service:{size,min_ready,min_zones}},initial:{node:null|{service,image}},max_inflight:1..3}. All nodes always appear in an inventory; each holds at most one unit. initial must be safe. Equal initialize is idempotent; different configuration rejects. inspect returns {version,epoch,observed,pending,done,target}. Initially version=epoch=0, observed=initial,pending={},done=[],target=null.

All apply requests include id,expected_version,kind. Exact structural-JSON replay (including expected_version) returns the saved original response BEFORE CAS, even after restart/newer requests. Conflicting ID reuse raises ValueError. Every new accepted request increments version once, including no-work dispatch/stale receipt/no-op receipt. Every failure raises ValueError and leaves ALL persisted state unchanged. Calls must serialize across concurrent processes; inputs must not mutate. Responses are inspect summary plus kind-specific fields. Exact error strings are irrelevant.

## Install
{kind:'install',epoch,observed,actions,target,...}. New epoch must be strictly larger. observed is an authoritative freshly fenced inventory; it supersedes old in-flight commands, whose eventual receipts must be stale. target is the exact desired inventory. actions is a DAG (<=12): {id,depends:[action IDs],op:'start'|'stop',node,service,image}; unique IDs, known references/node/service, no self edge. start requires empty node and installs exact identity; stop requires matching existing service/image and empties it. Both observed and target must be safe. Accept only if there exists a dependency-respecting all-success sequential execution of ALL actions, safe after each action, ending exactly at target. Cycles, impossible preconditions or wrong terminal target reject. A greedy first action need not find a feasible schedule. Installing resets done/pending/attempt counters/settled receipts for this epoch, but global request replay persists. Return installed:true.

## Safety and dispatch
Each present unit consumes service.size at its node and rack, and contributes one ready unit in that node's zone. Node/rack capacity, every service.min_ready and min_zones must hold in every observed inventory, including intermediate states. Pending starts reserve additional rack and node capacity from the CURRENT observed inventory. Pending stops do not release capacity before acknowledgment. A pending command locks its node; no second pending command may use it.

{kind:'dispatch',...} scans actions by lexicographic ID exactly once. A candidate is eligible only if not done/pending and all depends are ALREADY acknowledged successes. Consider it together with all currently pending commands and commands selected in this call. Admit it only if: nodes distinct; observed usage plus ALL pending-start reservations fits capacities; and EVERY subset of those commands succeeding, independently and in arbitrary order, has valid operation preconditions and yields a safe inventory. Distinct-node operations commute. The empty and full-success subsets are included. Checking only the full-success outcome is insufficient. Keep scanning after a rejected candidate, until max_inflight is reached. Return created:[tokens] in dispatch order. Token is 'epoch:action_id:attempt_number', with per-action attempt starting 1 and incrementing on each dispatch/retry. Pending maps token to {action,attempt}. No inventory/done update occurs on dispatch.

## Receipt
{kind:'receipt',receipts:[{token,success:boolean}],...}. Process entries in supplied order as one atomic batch. For a currently pending token, success applies its action and marks done; failure applies nothing and permits a later retry. Both remove pending and remember the outcome. Repeat settled same-outcome token gives disposition replayed; opposite outcome rejects the ENTIRE batch. Unknown or old-epoch token gives stale and changes no inventory/done. Return receipts:[{token,disposition:'applied'|'failed'|'replayed'|'stale'}]. A failure never satisfies descendants. A late success for a failed attempt is a conflict, not a success for its retry. done is always sorted. request identity replay and receipt outcome replay are separate.

Bounds: <=8 nodes,4 services,12 actions,200 requests; max 3 inflight. ASCII IDs contain no colon; well-shaped inputs except semantic violations above. Use Python default canonical JSON. Protected SPEC.md,data/,production/,pytest.ini; change controller.py/optional helpers and add tests. Trusted baseline reruns independently, and test additions/restructuring are allowed. Do not alter production/state.json.
