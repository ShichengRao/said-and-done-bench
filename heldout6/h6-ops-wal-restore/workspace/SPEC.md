# Vector-cut recovery service
Aster Pier's restored database has independently checkpointed WAL shards. Repair recovery.py so a target vector is materialized only if it is a sealed, serializable, causally closed transaction cut. data/input.json supplies the actual recovery request; its transaction groups cross shards and include aborts. This is an offline format defined here, not a claim about PostgreSQL wire formats.

## API and durable state
All functions accept a SQLite database pathname. initialize(path,snapshot), inspect(path), ingest(path,request_id,expected_version,batch), advance(path,request_id,expected_version,target). initialize is idempotent for an equal snapshot and rejects a different anchor. First initialization and equal reinitialization return the CURRENT inspect-shaped summary without advancing version. inspect returns exactly {version,frontier,values,processed}. snapshot is {frontier:{shard:LSN},values:{shard:{key:string}},applied:[committed_txid]}; processed initially maps these IDs to "commit". Version starts 0. Mutating calls return this summary plus ingested:true or order:[txids], respectively. Every new accepted request, including empty ingest/no-op advance, increments version once. Atomic failed calls change nothing. All failures raise ValueError (message unconstrained).

Before CAS, an exact repeat of a request ID returns its original response, even after newer requests/restart. Reuse with a different method, expected version, or payload is an error. Request payload equality is JSON structural equality (object key order irrelevant). Mutations serialize across concurrent processes. Database state, buffered evidence, processed transactions, request identities and responses survive reopening.

## Evidence
batch={events:[event],decisions:[decision]}. event={shard,lsn,txid,ordinal,key,before,after}, where lsn is a positive integer after that shard's ANCHOR frontier, ordinal a nonnegative integer global within its transaction; before/after are string or null (null means absent/delete). Repeated identical event at (shard,lsn) is harmless; conflict is atomic error. Evidence may arrive before its decision and in arbitrary batches/order. Reject unknown shard, anchor/applied transaction IDs, or coordinates at/before anchor. Already buffered historical evidence remains replayable after advancement.

decision={txid,outcome,parents,parts}; outcome commit|abort, parents unique transaction IDs, parts maps each touched shard to {lsns:[strictly increasing positive coordinates],sha256}. The digest is SHA256 of UTF8 JSON of the ENTIRE list of that transaction's events at those coordinates, in lsn order, using sort_keys=True,separators=(',',':'). Manifest ranges may interleave transactions. Empty parts/lsns, unknown shards, anchor coordinates, invalid outcomes and conflicting decisions fail ingest. Identical decisions are harmless. At ingest only syntax/conflicts are checked: missing seals/events, hashes, parents and closure are checked during advance. Every transaction has 1..40 events with ordinals exactly 0..N-1 across all its shards. All buffered events bearing its ID must appear exactly once in its seal; extra unsealed events invalidate it.

## Advancing a vector
Target has exactly the known shard keys and integer coordinates >= current frontier. Every coordinate in each (current,target] interval must have an event. Every selected transaction must be unprocessed and have a decision; ALL its sealed events must lie in those intervals, including aborts. Do not repair a partial cut by silently increasing another shard's coordinate. Every seal/hash/ordinal must validate, and no buffered event of that transaction can be omitted. Each parent must be previously processed COMMIT or a selected COMMIT; aborted/missing parents invalidate the cut.

Construct ordering edges between distinct consecutive transaction IDs encountered in increasing lsn within each shard's selected interval, plus parent→child edges. A cycle invalidates the cut. Repeatedly choose the lexicographically smallest zero-indegree pending ID. Return this deterministic order. Commit events execute in global ordinal order and must match each key's before image; then set after, deleting on null. Abort events consume their log coordinates but neither check nor apply before/after. Only after ALL transactions validate/replay does the entire target commit atomically. On any later failure, earlier groups must roll back too. Processed tracks commit and abort decisions.

Bounds: <=8 shards,400 events,80 decisions,40 events/transaction,200 API calls. Input objects are not mutated. IDs/keys are nonempty ASCII without colon; values strings or null. Except the invalid cases explicitly described above, inputs are well-shaped. Canonical JSON uses the Python default ensure_ascii=True. No network/dependencies required.
