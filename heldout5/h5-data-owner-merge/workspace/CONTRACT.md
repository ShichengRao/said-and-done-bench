# Ownership assignment before account merge
Nettle Support needs a deployable owner assignment for every merge group. Each group combines accounts that must retain one accountable owner; separate groups can be required to use different owners under the supplied conflict-of-interest policy. Producing a candidate list alone does not authorize the merge.

## Sources
`request.json` is `{at:int,groups:[{id:string,units:positive int,scopes:[string]}],separate:[[group_id,group_id]]}`. Each group's scopes are all required. Each separate pair must receive different owners, regardless of spare capacity. Group ids are unique and references exist. Duplicate separate pairs are harmless. At most seven groups, four owners, eight proposals.

`owners.json` is a list of `{id:string,from:int,until:int|null,capacity:int}` with unique ids and nonnegative capacity. An owner is active on `[from,until)`, null unbounded. `reservations.json` is a list of `{owner,from,until,units}`; entries are separate reservations, each subtracts units during the same half-open interval. Negative remaining capacity raises `ValueError`. An assignment consumes each group's units on its assigned owner; capacities are shared across all groups.

`authority.json` lists `{seq:int,at:int,owner:string,scope:string,op:'grant'|'revoke',until:int|null}`. Ignore events with at > request.at. Deduplicate identical seq rows and reject conflicting in-window seq objects with `ValueError`. Replay remaining events in seq order. Grant replaces that `(owner,scope)` interval's expiry; revoke removes it. A final grant covers the request only while at < until, null unbounded. Expiry does not resurrect an older grant. Candidate owners are active owners holding every group scope at request.at. All lists are unordered; owner and scope refs are valid.

`proposals.json` is the owner's catalog of possible future authorizations: `{id:string,group:string,owner:string,cost:positive int}`. Approving one proposal would authorize that active owner for all required scopes of that one group, in addition to present candidates. It does not increase capacity or waive separation, and cannot activate an inactive owner. Proposals are **not current grants**. Each has a unique id. The engineer may recommend a subset but cannot apply it.

## Output
Return exactly `{ready,candidates,available_units,assignment,infeasible_core,owner_remedy,blocker_codes}`. `candidates` maps every group id to sorted current candidate owner ids. `available_units` maps owner ids to integer remaining capacity. A valid assignment maps every group id to one candidate owner, satisfying all shared capacities and separation pairs. If one exists, return `ready=true`, the lexicographically first assignment (owner tuple in sorted group order), empty core, null remedy and `blocker_codes=[]`.

If none exists, return `ready=false`, `assignment={}`, `blocker_codes=['owner_assignment_infeasible']`, and the smallest-cardinality infeasible subset of groups under the same capacities and induced separation pairs; ties use sorted group-id tuple order. `owner_remedy` is null if no subset of the proposed authorizations makes the whole request feasible. Otherwise return `{proposals:[sorted ids],cost:int,assignment:{...}}` for the subset with minimum sum of costs (tie: lexicographic tuple of proposal ids), plus the lexicographically first resulting valid assignment. Owner approval of these authorizations is required before this merge can be released; a successful counterfactual is not current authority.
