# Durable refund reservation and reversal service

Implement `refunds.initialize(path,captures)`, `refunds.apply(path,command)`, and `refunds.snapshot(path)` in standard-library Python using SQLite. A merchant refund can draw from several captures, settle in parts, expire with unused holds, and later reverse a specific settlement. Preserve accounting under retry, restart, optimistic version conflicts and simultaneous callers. A single transactional JSON state row is acceptable. All data are fictional. SPEC.md and data/ are immutable; code/tests can be edited or added. Original examples are independently rerun.

## Inputs and durable identity
IDs contain ASCII letters/digits/hyphens. Captures are unique `{id,merchant,currency,captured_cents,refund_until}` with nonnegative integer cents and positive integer deadline. initialize returns None, creates clock 0 with no refunds/settlements/history, and persists the seed. Reinitializing with the same captures in any order is a no-op; a different seed raises ValueError without changes. Parent directory exists. Inputs below have exactly the declared fields and valid types; lists of candidates have unique IDs, cents is positive for all commands, at >=0. Do not mutate inputs or alias returned objects.

Every command has operation_id, at, kind plus the fields below. Accepted operation_id identifies the ENTIRE JSON command, dictionary order ignored but list order meaningful. Identical replay returns its ORIGINAL response before checking time, expiry or versions; altered reuse raises ValueError. Persist identity across processes. New commands require at >= stored clock. New calls first tentatively expire every held refund with expires <= at: zero its allocations, status expired, increment version once. Then perform the requested operation. Any ValueError rolls back EVERYTHING, including these expirations, clock, history and operation identity. Rejected IDs remain reusable. Accepted unavailable reservations DO advance time and commit expirations. No wall clock is used.

## Operations
reserve adds `{refund,merchant,currency,cents,until,candidates}`. Refund ID must not exist; until > at. Unknown candidate capture IDs raise ValueError. Iterate candidates in their supplied order, skipping different merchant/currency or refund_until <= at. Available cents is captured minus net settled (settlement minus reversal) minus all current holds. Take as much as needed from each eligible capture until the requested amount is met. If insufficient, result unavailable with refund null: create no refund or partial hold and the refund ID remains reusable. Otherwise create version 1/status held. Its expires is the minimum of until and refund_until of captures actually allocated; capture-window expiry releases the WHOLE remaining refund hold. Allocation order is the candidate order, omitting captures assigned zero.

settle adds `{refund,expected_version,cents}`. Refund must be held AFTER tentative expiry and version must match. Cents may not exceed remaining held amount. Consume its current allocations in their existing order. Create a durable settlement with ID equal to this operation_id and per-capture consumed amounts. Increase gross settled_cents, increment refund version once; status becomes settled only when all held allocations reach zero, otherwise stays held. Keep zero allocation entries in the refund.

reverse adds `{settlement,expected_version,cents}`. Settlement must exist. Version refers to its refund. Any refund status is allowed. Reverse no more than that settlement's not-yet-reversed amount, consuming its original allocation order and recording cumulative per-capture reversed amounts. This restores capture availability and increments refund reversed_cents and version. It does NOT restore holds or change refund status, even if fully reversed. Reversals are tied to the referenced settlement, not a merchant's overall refunded balance.

release adds `{refund,expected_version}`. Requires a held refund and exact version; zero remaining allocations, status released, version increment. All unknown IDs, stale versions, non-held settle/release, excessive settle/reverse, and operation reuse conflicts raise ValueError atomically. Each operation is one transaction, including identity lookup, expiration, balance checks and history.

## Results
A refund object is exactly `{id,merchant,currency,requested_cents,expires,version,status,settled_cents,reversed_cents,allocations}`. Allocations is an ordered list of `{capture,cents}` for CURRENT remaining holds. Settled cents is cumulative gross, reversed cents cumulative reversals; net is their difference. Both remain even after release/expiry. An operation returns exactly `{operation_id,result,refund}` where result is reserved, unavailable, settled, reversed or released, and refund is the post-operation refund object or null. Store immutable historical responses; later settlement/reversal cannot change a past response.

A settlement is `{id,refund,allocations}` with allocations `{capture,cents,reversed_cents}` in original consumed order, omitting zero consumed rows. snapshot returns exactly `{clock,captures,refunds,settlements,history}`. Captures sort by ID and include their seed fields plus refunded_cents (net across all settlements), held_cents and available_cents. Refunds and settlements sort by ID. History lists accepted responses in commit order, once per operation. Snapshot observes one coherent durable state and never advances time. Any serial winner among simultaneous calls is valid; do not require a particular thread to win.
