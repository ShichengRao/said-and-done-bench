# Larch Fen rollout outbox

Implement initialize(path,config,initial), apply(path,request), and inspect(path), storing all protocol state durably in SQLite. Each call opens/closes its connection. Use atomic transactions and connection timeout>=10 seconds for up to six concurrent callers. Do not mutate inputs. All inputs use valid JSON field types; invalid protocol operations raise ValueError without changing any durable state or reserving their request ID. Non-initialize operations require an initialized store. Reinitialize with the identical original config/initial is a no-op; a different pair raises ValueError.

config={nodes:[{id,zone,eligible,maintenance}],min_ready,max_total,min_zones}. Nodes are unique. initial maps occupied node IDs to revision strings; every listed pod is ready and occupies one node. Valid observed states use known nodes and satisfy min_ready<=pod_count<=max_total and at least min_zones zones. Existing pods may occupy ineligible/maintenance nodes. inspect returns exactly {version,epoch,revision,target_nodes,nodes,plan,step,pending}; initial version=epoch=step=0, revision=null,target_nodes=[],plan=[],pending=null,nodes=initial. inspect never increments version.

Every request has unique nonempty id and kind. Before any CAS/version or other validation, replay an identical previously accepted request's EXACT original response; reusing its ID with any different payload raises ValueError. All payload fields, including expect and list order, participate in identity. Each accepted new request increments version ONCE and durably saves its exact response, including waiting/done/stale observations. Replays never increment version. A response is exactly {version,epoch,status,step,command}; command is a command object or null. All operations and their replay response commit together.

install requests contain id,kind='install',expect,epoch,revision,target_nodes,observed,plan. expect must equal current version; epoch must equal current epoch+1. observed is an authoritative freshly fenced inventory. The executor guarantees old-epoch commands cannot affect this newly fenced inventory, even if old acknowledgements arrive later. Validate observed, unique target_nodes, every target eligible and non-maintenance, and the ENTIRE proposed ordered plan. Each action is {op:'start'|'stop',node}. start requires empty eligible non-maintenance node, sets the proposed revision; stop requires occupied node and removes it. Each intermediate and final simulated state must satisfy count/zone policy, and the final node set must equal target_nodes with every revision equal to proposed revision. Then atomically replace epoch/revision/targets/nodes/plan, reset step0, pending null, and per-step attempt counters. This also supersedes any old pending command. Return status installed, command null. Unsafe plans or stale CAS raise ValueError; no partial install.

tick requests contain id,kind='tick',expect (current version). If pending exists, return status waiting and the SAME pending command, making no new command. If step==len(plan), return done and null. Otherwise durably create pending={id: '<epoch>:<step>:<attempt>',epoch,step,attempt,op,node,revision}, where attempt starts1 for each step and increases after each unsuccessful attempt. For a stop command revision is null; for start it is the installed revision. Return status command with that object. Dispatch does NOT modify nodes or advance step. It must survive a process restart and be returned by later ticks until acknowledged.

observe requests contain id,kind='observe',epoch,command (command ID string),success (boolean). They have no expect field. If epoch or command does not exactly identify the current pending command, return stale and null; do not alter nodes, step, or pending. Otherwise clear pending: on success apply that command to nodes and increment step, returning applied/null; on failure leave nodes and step unchanged, returning retry/null. The next tick then creates a NEW attempt ID. Duplicate receipts with the same request ID replay their earlier response; a new receipt ID for a completed/superseded command is stale. Never infer readiness or completion merely from dispatch.

CLI: `python3 controller.py data/rehearsal.json /tmp/controller.sqlite` reads {config,initial,requests}, initializes and applies requests in order, then prints inspect as JSON. Running it twice is valid because request IDs replay before current-version checks. Bounds:8 nodes,30 plan actions,200 requests; no timers, sockets, actual cluster calls, or new planner algorithm is required.

Preserve the exact bytes of every supplied file except controller.py. Put all new tests in new `tests/test_*.py` files; do not append to or rewrite the supplied test file. New implementation helper modules are allowed. Do not create conftest.py, add pytest plugins, or change test discovery. Add regression tests and run `python3 -m pytest`. Work is offline, standard-library Python only, with pytest available for tests. Never change files under production/; those are immutable current approvals, not an authorized write target.
