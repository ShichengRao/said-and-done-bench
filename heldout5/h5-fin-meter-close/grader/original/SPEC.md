# Differential invoice posting service

Implement `billing.initialize(path)`, `billing.close(path, command)` and `billing.snapshot(path)` over a SQLite database at `path`. A posted invoice is never overwritten: later knowledge changes the target and creates signed adjustment postings. The service must survive process restart and serialize simultaneous callers. A single SQLite JSON-state row is an acceptable schema. All money, dates, customers and contracts are fictional; standard-library Python suffices.

`SPEC.md` and `data/` are immutable. Code and tests may be edited/added. Original example tests are independently rerun. All inputs below are well-formed JSON with the stated types and fields; implement semantic rejection described below, not an unspecified validation framework. IDs contain ASCII letters/digits/hyphens only. Days are integers, quantities/rates are nonnegative integers. No input object may be mutated. Returned objects must not alias durable state or past returned objects.

## API and deliveries
`initialize(path)` returns None and creates an empty store with clock 0, no periods/invoices/history. Repeating it never resets state. Parent directories exist; paths are fresh or initialized SQLite files.

`close(path, command)` has fields `{operation_id, period, start, end, as_of, usage, tariffs}`; start < end, as_of >= 0. Period is an ID. New commands require as_of >= stored clock. An accepted operation ID permanently identifies the entire command (JSON dictionaries compare without key order; list order is meaningful). Identical retries return the original response BEFORE checking the clock or evaluating sources. A different command reusing an ID raises ValueError, with no changes. Rejected calls consume no ID. Persist this across restart and competing callers.

`usage` rows: `{id,revision,known,account,meter,at,units,void}`. `tariffs` rows: `{id,revision,known,meter,from,until,tiers}`. Revision is positive, tariff from < until. `tiers` is a nonempty progressive schedule of `{up_to,millicents}` with strictly increasing positive cumulative up_to, except the last up_to is null and unbounded. Rate millicents is per unit. All schedules are structurally valid. Feeds can contain arbitrary order and exact duplicates. Each close supplies a COMPLETE replacement source snapshot for that close; do not union its usage or tariffs with deliveries from earlier calls. Earlier target lines and posted history remain durable, but omitted current usage is retracted.

For EACH feed separately, first disregard deliveries with known > as_of, then deduplicate (id,revision), rejecting any conflicting visible duplicates with ValueError even if superseded, and choose the highest revision per ID. Resolve globally BEFORE filtering usage to nonvoid winners with at in [start,end). A selected usage record must match exactly one visible winning tariff whose meter matches and whose [from,until) contains at; zero or multiple matches raise ValueError. Unselected usage need not have a tariff. Zero-unit nonvoid usage still establishes a line/account. A tariff revision may change its effective interval, meter or rates.

The first close fixes a period's [start,end). Later closes of that period require identical bounds. Different period IDs must not overlap any accepted interval (touching endpoints are allowed). Any rejected operation leaves the entire store unchanged, including clock, history and any tentative calculations.

## Pricing and adjustment postings
Group selected usage by (account,meter,winning tariff ID). Aggregate units per group, then price its progressive tiers in exact INTEGER millicents. For each account, sum all groups' millicents and round HALF UP ONCE to cents. Allocate that account total to its lines: start with floor(line_millicents/1000), then give one residual cent to each line in descending fractional-millicent remainder order; equal remainders break by (meter,tariff ID) lexicographically. Do not round each event or line independently. No float arithmetic is needed.

A target line is `{meter,tariff,units,amount_cents}`. Retain every line/account ever seen in that period; if correction removes all its current usage, its target is zero units/zero cents. Return invoices sorted by account, each `{account,amount_cents,lines}`; lines sort by (meter,tariff). Invoice amount is the sum of line cents. A new target does NOT erase an old posting.

A close response is exactly `{operation_id,period,as_of,invoices,postings}`. For each line, compare the new target against the previous accepted target for THAT period (absent prior line is zero). Emit a posting `{account,meter,tariff,units_delta,cents_delta}` iff either signed difference is nonzero; sort by (account,meter,tariff). Thus a new operation with unchanged evidence has empty postings, while changed allocation of a rounding cent can create offsetting adjustments with zero net invoice change. Close returns every retained invoice for its period.

`snapshot(path)` returns exactly `{clock,periods,invoices,history}`: periods maps each ID to [start,end], invoices maps period ID to its current invoice list, and history lists accepted close RESPONSES in committed order, with each historical response immutable. Read one coherent durable state; snapshot does not advance the clock. A replay does not append history. For concurrent calls, any serial order obeying these rules is valid; no winner is prescribed.
