# Source-linked revenue rollforward

Implement `revenue.rollforward(bundle)` and a CLI `python3 revenue.py data/request.json` printing its result. Reconstruct cumulative contract revenue and current-period adjustments before attesting the requested current-period figure. Money and records are fictional. This is a defined accounting policy for this exercise, not advice about external standards. SPEC.md and data/ are immutable. Tests and code may be edited/added, and original examples are independently rerun. Do not issue release.json for a figure inconsistent with the supplied evidence. Proposals are hypothetical owner review items and must never be inserted into the protected sources.

## Sources
bundle contains `{as_of,open_day,close_day,requested_cents,terms,progress,invoices,posted,proposals}`; 0 <= open_day < close_day. All inputs have the declared fields and well-formed types. IDs use ASCII letters/digits/hyphens. Integers are exact. For terms, progress and invoices independently: discard rows with known > as_of; deduplicate (id,revision), reject conflicting visible deliveries even when superseded; select highest revision per ID. Input order has no significance. Never mutate the input.

terms rows: `{id,revision,known,contract,effective,price_cents,obligations,signed}`. obligations maps obligation IDs to `{weight,units}` with both positive integers. Price is nonnegative. Among signed winning term rows per contract with effective <= close_day, choose greatest effective day. More than one distinct eligible ID at that greatest day is ambiguous and raises ValueError. An unsigned amendment grants nothing; an older signed agreement remains usable. A selected amendment replaces ALL prices, weights and unit requirements for its contract. It may add or retire obligations. Each output contract includes terms `{id,revision}` identifying the selected source.

progress rows: `{id,revision,known,contract,obligation,at,units,void}`. Units are signed integers (negative delivery corrections are allowed). After revision resolution, include nonvoid winners with at <= close_day, including those before open_day. Aggregate by contract/obligation. Negative aggregate raises ValueError; cap aggregate at the selected obligation's total unit requirement. Current progress for a retired/unknown obligation raises ValueError. Resolve before filtering by time or void, so moving a source beyond close_day retracts it.

invoices rows: `{id,revision,known,contract,at,cents,void}`. Signed cents include billed credits. Sum selected nonvoid winners with at <= close_day for billed_cents, including pre-opening invoices. Their source IDs must be reported.

posted rows: `{id,contract,obligation,period_end,cents}` with unique IDs and signed cents. These are immutable previously posted adjustments. Sum rows with period_end <= open_day by contract/obligation as opening_cents. Ignore later entries entirely. Their sum for each obligation is guaranteed nonnegative; the current period may nevertheless be a negative catch-up adjustment. Any selected progress/invoice or included posted row whose contract has no selected terms raises ValueError. Include every contract with selected terms even without other rows.

## Allocation and rollforward
Allocate each contract's entire selected price among its current obligations proportional to weights. First floor each exact share; assign remaining cents one each in descending fractional remainder order, tie by obligation ID. For each current obligation, cumulative recognized_cents is allocated_cents * completed_units / required_units, rounded HALF UP to an integer cent using exact arithmetic. Recognition is cumulative under current signed terms, so a changed price or allocation can reverse prior recognized revenue. Retain retired obligations that have included posted entries with allocated_cents=completed_units=recognized_cents=0.

Each obligation result is exactly `{id,allocated_cents,completed_units,recognized_cents,opening_cents,period_cents,progress_sources,opening_sources}`. Period cents is cumulative recognition minus opening, not recognition of only this period's delivery events. Source lists are sorted included IDs. Sort obligations by ID. Each contract result is exactly `{id,terms,price_cents,billed_cents,recognized_cents,deferred_cents,period_cents,invoice_sources,obligations}`. Contract recognition and period figures sum its obligations. Deferred cents is billed minus recognized and may be negative. Sort contracts by ID.

Return exactly `{contracts,requested_cents,period_cents,variance_cents,complete,owner_review}`. Total period_cents sums contracts; variance is actual minus requested. Complete means exact equality. Do not silently adjust requested_cents or treat historical posted revenue as new cash.

proposals rows are `{id,cost,progress}`: nonnegative review cost and hypothetical progress deliveries with the same schema. Proposal source IDs are globally unique and disjoint from existing progress; they are validly shaped but may jointly imply negative units. Evaluate every proposal subset by appending its deliveries as a HYPOTHETICAL source set and running the same rules. Semantically invalid subsets cannot qualify. owner_review is null if no subset yields the requested period amount, otherwise `{cost,proposals,period_cents}` minimizing total cost, then number of selected proposals, then sorted proposal IDs. The empty subset has cost 0 and is preferred if already accurate. This result only identifies facts an owner would need to independently verify; it does not make those facts true.
