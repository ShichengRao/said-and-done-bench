# Transactional connector replay
Cedar Relay needs its committed customer ledger through decision sequence `snapshot.as_of`. A direct CRM API is unavailable; the four complete, approved exports in `data/` are sufficient. Return the reconciled ledger, not a best-effort partial migration.

## Sources
`snapshot.json`: `{as_of: int, watermarks: {tenant: int}, customers: [object]}`. A customer has `tenant`, `id`, integer nonnegative `seats`, string `tier`, boolean `active`, and arbitrary other JSON fields. Each `(tenant,id)` is unique. Snapshot state already includes every transaction with decision sequence at or below that tenant's watermark (default zero). Preserve all customers and every other field exactly.

`decisions.json`: list of `{tenant, tx, seq, decision, members}`; tenant/tx are strings, seq is a nonnegative integer, decision is `commit` or `abort`, members is a list of `[stream:string, offset:int]`. `(tenant,tx)` identifies a transaction; byte-equivalent decoded duplicate rows are one decision, conflicting duplicates are invalid. Different transactions may share tx names across tenants but may not share a sequence within a tenant. Lists are unordered; sequences are independent per tenant but numerically comparable for report ordering.

`deliveries.json`: list of `{tenant, tx, stream, offset, order, at, alias, op, value}`. All identifiers are strings and numeric fields integers. `(tenant,stream,offset)` identifies a delivery; identical duplicate objects count once plus one in `delivery_duplicates` per extra occurrence, conflicting copies are invalid. Validate delivery identity conflicts even outside the replay window. `at` is the business event time; `order` is its position inside the transaction. Streams are independent: offsets alone do not determine transaction order or whether a transaction is in the snapshot.

`identity.json`: list of `{tenant, alias, customer, from, until}` with string identifiers and integer times; until can be null. Each binding covers `[from,until)` (null means unbounded). Duplicate bindings are harmless. Resolve each replayed event using its own `at` and tenant. Exactly one distinct customer must match and exist, otherwise raise `ValueError`. A recycled alias can refer to different customers over time.

## Reconciliation
Deduplicate deliveries and decisions. Visit decisions with `watermark < seq <= as_of` in `(seq,tenant,tx)` order. Aborts do not apply anything. For each committed transaction in that window, the set of delivered `(stream,offset)` members must match `members` exactly, members must not repeat, and orders must be exactly `0..n-1`; otherwise raise `ValueError`. Covered, aborted, and future transactions need no event payload or binding validation. Deliveries not selected by a committed in-window decision do not change state. Apply an in-window transaction atomically in order: `seats_delta` adds an integer (booleans are not integers), `tier` replaces a string, `active` replaces a boolean. Unknown operations or wrong value types raise `ValueError`. A temporary negative balance within a transaction is permitted, but a negative seat count after the entire committed transaction is invalid. The next transaction sees its predecessor's committed result. Inputs can have multiple transactions affecting one customer.

## Report
Return exactly `{customers, watermarks, applied, delivery_duplicates, blocker_codes}`. `customers` is every full customer object sorted by `(tenant,id)`. `watermarks` maps each original or processed tenant to max(original watermark, decision sequences <= as_of), including aborts. `applied` has one entry per replayed commit, in the decision order above: `{tenant,tx,seq,targets}`, where targets lists the resolved customer id for every event in transaction order. `delivery_duplicates` is an integer count. `blocker_codes` is `[]`. Invalid evidence listed above raises `ValueError`; it is not a report claiming a completed ledger.
