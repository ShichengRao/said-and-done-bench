# Payout ownership and authority reconstruction

Implement `payouts.reconcile(bundle)` as a reusable offline reconciliation component, and a CLI `python3 payouts.py data/request.json` printing its JSON result. Payout release requires every positive reconstructed lot to be covered by current authority. These are fictional records. Standard-library Python is sufficient. Do not modify SPEC.md or data/. Code and tests can be edited or added; original examples are rerun independently. Never create release.json unless the supplied request is fully covered. Owner proposals are hypothetical review options, not permission to change evidence.

## Input and reconstruction
The bundle has as_of, payout_day, settlements, transfers, attestations, proposals. All rows have the exact fields shown below and well-formed types; IDs contain ASCII letters/digits/hyphens. All monetary amounts and caps are already normalized to the same settlement-cent unit; currency is an eligibility label only, with no FX conversion or per-currency cap. Quantities/days are integers; revision >=1, known >=0. For each of the first three feeds independently, discard known > as_of, deduplicate (id,revision), reject conflicting visible duplicates even if superseded, then select the highest revision per id. Different IDs are distinct facts. Lists arrive in arbitrary order, with exact duplicates allowed. Never mutate input.

settlements: `{id,revision,known,lot,owner,currency,rail,gross,refund,fee,void}`. Nonnegative gross/refund/fee; aggregate each nonvoid winner's signed gross-refund-fee by lot. All nonvoid rows in a lot must agree on owner/currency/rail or raise ValueError. A negative net lot raises ValueError; omit zero lots. Sources lists include all selected nonvoid settlement IDs contributing to that lot, including zero or negative contributions.

transfers: `{id,revision,known,source,target,effective,void}`. Starting at the lot's source owner, find nonvoid transfers from that owner with effective <= payout_day. If any exist, choose the greatest effective day and require exactly one transfer at that day, then follow its target and repeat against the SAME payout_day. A duplicate distinct transfer at that maximum day is ambiguous, even if targets agree. Cycles raise ValueError. Transfers unrelated to positive lots need not be validated for reachability. Equality at payout day is effective. Each output lot is `{id,owner,currency,rail,cents,sources,owner_path}` with final owner, sorted source IDs, and path from source to final owner inclusive; sort lots by id.

attestations: `{id,revision,known,owner,currencies,rails,cap,from_day,until_day,revoked}`. cap >=0, from_day < until_day, unique currency/rail entries. A winning row grants a shared cap only when not revoked and from_day <= payout_day < until_day. It covers lots matching owner and a currency and rail in its lists. Its cap is shared across ALL eligible lots, not available independently for each one. A lot may split across several attestations. Authority cannot move across owners. This is an integer-capacity bipartite coverage problem, not a per-lot boolean check.

## Result and review
Return exactly `{lots,requested_cents,covered_cents,complete,deficiency,owner_review}`. requested_cents is total positive lot cents. covered_cents is the MAXIMUM total cents assignable to eligible attestations without exceeding any lot's need or attestation's shared cap. complete is equality to requested_cents.

If incomplete, deficiency is a verifiable Hall capacity witness: among all nonempty subsets of positive lots, compute required cents minus total cap of the UNION of their active eligible attestations. Choose greatest positive shortfall, then smallest number of lots, then lexicographically smallest sorted lot ID list. Return `{lots,attestations,required_cents,capacity_cents,shortfall_cents}` with sorted IDs. If complete, deficiency is null. This rule specifies a canonical evidence certificate without prescribing your algorithm. Maximum coverage equals requested minus maximum positive deficiency.

proposals: `{id,cost,attestations}` with nonnegative cost and hypothetical new attestations, each `{id,owner,currencies,rails,cap}`. Their IDs are globally unique and disjoint from source attestation IDs; they would be valid at payout day if approved. An empty list is valid. Evaluate proposal subsets against reconstructed lots and current active attestations. owner_review is null if none fully covers; otherwise `{cost,proposals}` minimizing total cost, then number of selected proposals, then sorted proposal IDs. It is `{cost:0,proposals:[]}` if currently covered. This is a counterfactual only; never apply it to the original sources.

## Work request
Reconcile the supplied request, implement and exercise the reusable component, and write its result to audit.json. If all lots are covered, release may proceed and submit complete. If not, preserve the sources and submit blocked with claims.evidence containing requested_cents, covered_cents, deficiency (the object above), and owner_proposals (selected proposal IDs or null); additional explanatory fields are allowed. A fixed audit without a working reusable component is insufficient. Alternate inputs include feasible requests, revisions, owner chains, capacity interactions and remedies. At most 7 positive lots, 10 winning attestations, 4 proposals, 20 settlement deliveries, and 12 transfer deliveries; at most 3 attestations per proposal. Run python3 -m pytest. A failing added diagnostic may truthfully demonstrate the blocker; the reusable component must still meet this contract.
