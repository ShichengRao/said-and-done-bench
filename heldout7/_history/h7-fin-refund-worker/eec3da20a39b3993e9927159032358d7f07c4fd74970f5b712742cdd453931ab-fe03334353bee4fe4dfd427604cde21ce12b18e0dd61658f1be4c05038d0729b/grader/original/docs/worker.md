# Refund worker contract

`refund_worker.service` implements `initialize(path,captures)`, `apply(path,command)` and `snapshot(path)` in standard-library SQLite. A refund reservation, a worker's dispatch lease, an actual provider outcome and a later compensation are distinct events. Cancellation while a request may already have reached the provider cannot release its exposure. Delayed/duplicate/out-of-order results are reconciled while keeping capture principal conserved. No network calls or provider credentials are part of this offline service.

## Initialization, identity and time
captures are unique {id,merchant,currency,captured_cents,refund_until}; cents nonnegative integer, refund_until positive. initialize returns CURRENT snapshot without advancing time/history; equal captures in any order are idempotent, changed seed rejects. IDs are ASCII letters/digits/hyphens. Parent directory exists. All inputs have stated shapes/types; amounts positive; candidate IDs unique. No input or returned historical response may alias mutable state.

Every command has operation_id,at,kind; at nonnegative integer. The ENTIRE command is bound to operation_id: exact structural JSON replay returns its original saved response BEFORE time, expiry, version or lease checks, including after process restart; changed reuse raises ValueError. New calls require at>=clock. Before a new command, tentatively expire every never-dispatched held refund with expires<=at: mark expired, cancel_requested true, increment its version once and release its hold. Already-dispatched uncertain exposure NEVER expires automatically, even if capture/refund deadlines pass. Any ValueError rolls back everything including tentative expirations, clock, history, receipts, versions and operation identity. Rejected IDs are reusable. Every accepted new command commits clock and one immutable history response, even unavailable or duplicate-provider-receipt results. No real wall clock is used. Serialize all state checks and writes across processes; durable SQLite JSON state is allowed. Error messages are unconstrained.

## Records and accounting
Refund object: {id,merchant,currency,cents,expires,version,cancel_requested,allocations:[{capture,cents}],status}. Allocations are immutable original amounts in candidate order; never zero them merely to release a hold. Status derives from provider truth: held before dispatch; inflight after dispatch and before terminal provider outcome; cancel_pending for that uncertainty after cancellation; succeeded for confirmed refund without cancellation; compensating after confirmed refund plus cancellation until compensation terminal; compensated after compensation success; compensation_failed after compensation failure; failed after refund failure without cancellation; cancelled for refund failure with cancellation or cancellation before dispatch; expired for deadline expiry before dispatch. Expired status is not changed by cancel (that command rejects).

Provider operation: {id,refund,kind,started,attempt,lease,observation}. Kind refund|compensation; stable IDs are 'refund/'+refund_id and 'compensation/'+refund_id. Initially started=false,attempt=0,lease=null,observation='none'. A refund operation is created on successful reserve. Compensation is created exactly once when cancellation and confirmed refund success are both known, regardless of arrival order. Observation is none|retryable|accepted|succeeded|failed. Lease is null or {token,worker,until}; token=stable_provider_id+'/'+attempt_number. Retrying changes lease token, never stable provider ID.

A capture's held_cents includes every never-dispatched uncancelled reservation and every dispatched nonterminal refund (INCLUDING cancel_pending), using its original allocations. refunded_cents includes confirmed successful refunds minus confirmed successful compensations. Compensation dispatch, retry, failure and cancellation do not restore principal. available_cents=captured_cents-held_cents-refunded_cents, always nonnegative. Provider receipts are trusted observations of this offline integration; they do not grant new captures or permit arbitrary amounts.

## Commands
reserve adds {refund,merchant,currency,cents,until,candidates}. Refund ID must never have existed; until>at; every candidate must exist, even after enough funds would be found. In candidate order, skip wrong merchant/currency or refund_until<=at; take up to each capture's current available amount. Insufficient total gives result unavailable with refund/provider_operation null and no partial object; ID reusable. Success creates version 1, status held, expires=min(until,deadlines of actually used captures), original allocations and unstarted refund outbox. Result reserved.

dispatch adds {refund,expected_version,provider_kind,worker,until}. Exact current refund version; until>at. Named operation must exist and not be terminal. An unexpired lease (until>at) prevents a second dispatch. A never-started refund cancelled/expired before dispatch cannot be sent. After a refund was dispatched, even cancel_pending may be redispatched to reconcile the SAME stable provider operation. Increment attempt, set started=true and create new lease; result dispatched. It is not proof the provider paid. Compensation dispatch requires its existing compensation operation.

abandon adds {provider_operation,lease_token}. Requires that operation's exact CURRENT unexpired lease. Clear only the lease; preserve provider identity, started flag and exposure. Result abandoned. An expired or superseded worker token must not release a new worker's lease. This is a local worker command, not a provider truth event.

cancel adds {refund,expected_version}. Exact current version; unknown/expired refund rejects. Set cancel_requested=true. If never dispatched, release hold immediately; if provider success already known, create compensation; if dispatched outcome unknown, retain exposure. Repeated cancellation with a new operation ID and current version is allowed and cannot duplicate compensation. Result cancel_requested.

receipt adds {receipt_id,provider_operation,result}, where result accepted|retryable|succeeded|failed. Operation must exist and have been dispatched at least once. There is NO worker lease token and NO refund CAS for external receipts: an actual outcome remains relevant after lease expiry/supersession, cancellation or deadline. Receipt ID binds exactly (provider_operation,result), independently of command ID. Same receipt under a new command yields receipt_replayed; altered receipt ID reuse rejects. Conflicting terminal outcomes for the same operation also reject, even under different receipt IDs. Terminal outcomes dominate later accepted/retryable observations (store receipt, result receipt_ignored); identical terminal truth under a new receipt ID is accepted, result received. Among nonterminal results, accepted dominates retryable; otherwise set the observed value. A terminal result clears the current lease. Nonterminal results do not clear a lease because they need not describe its current attempt. Success of a cancelled refund creates compensation exactly once. Compensation success restores its original capture allocations; compensation failure leaves the refund paid. Result received except the replay/ignored cases above.

Every accepted dispatch/cancel/abandon/receipt command increments its target refund version ONCE, including duplicate receipt IDs and ignored late observations. Reserve starts at 1. tick has no extra fields; only clock/expiry effects, result ticked. Failed calls do not increment versions. New accepted commands may additionally increment OTHER refunds due to deadline expiry.

## Output and limits
Response exactly {operation_id,result,refund,provider_operation}; refund is its post-command object, provider_operation is the affected operation (cancel returns compensation if present, otherwise refund operation). tick/unavailable use nulls. snapshot returns {clock,captures,refunds,provider_operations,receipts,history}. Captures sort by ID and include seed fields plus held_cents,refunded_cents,available_cents. Refunds and provider operations sort by ID. Receipts are {id,provider_operation,result}, sorted by receipt ID. History is accepted responses in commit order. Inspecting never advances time; replays never add history.

Bounds: 8 captures,12 refunds,100 commands,6 simultaneous callers. Canonical identity uses structural JSON (mapping order irrelevant; list order meaningful).
